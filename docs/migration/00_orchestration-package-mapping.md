# 00_orchestration - package mapping

Source: `ssis/00_orchestration/` (9 master packages generated by `build_orchestration_packages.py`
from `ssis/orchestration-plan.json`; run-time semantics in `deployment/ssis/Invoke-EstateOrchestration.ps1`).
Target: bundle `databricks/00_orchestration/` (`wwi_00_orchestration`), one Databricks Job per master,
generated by `tools/build_jobs_from_plan.py` from the same plan. The shared control layer it (and every
other project) uses is `databricks/common/` (`dbx_etl_common`, documented in `databricks/common/README.md`).

## Plan node -> task mapping

| Plan construct | Databricks task(s) | Notebook | Control-framework call |
|---|---|---|---|
| `batch_start` | `Start_Batch` | `notebooks/batch_start.py` | `control.startBatch(spark, catalog, batchName, batchType, businessDate, environmentCode, allowAdoptRunning=<RestartFromStep != "">)`; a non-zero `BatchId` parameter adopts that batch instead. Publishes task value `BatchId`. |
| `batch_end` | `End_Batch` (`run_if: ALL_DONE`) | `notebooks/batch_end.py` | `control.endBatch(spark, catalog, batchId)` - status derived like `usp_EndBatch`; publishes `BatchStatus`, fails the task if the batch failed. |
| `phase` | `<Phase>__start` -> children -> `<Phase>__end` | `step_start.py`, `run_child_package.py`, `step_end.py` | `control.startBatchStep(spark, catalog, batchId, stepName, stepSequence, stepGroup)`; `control.endBatchStep(spark, catalog, batchStepId, status)` - `__end` runs `ALL_DONE`, inspects the child tasks through the Jobs API and ends the step `Failed` (raising) if any child failed, so downstream `Failure`/`Success` edges see the SSIS phase outcome. |
| phase child (`children[]`) | `<Phase>__<Package>` | `notebooks/run_child_package.py` | Triggers the owning project's job `wwi_<NN_project>` (`PROJECT_JOBS` in the generator, looked up by name) with `only=[<Package>]` and the plan's `parameters` as `job_parameters` (`BatchId` from the `Start_Batch` task value, `BusinessDate`/`ReloadFullHistory`/`EnvironmentCode`/`RestartFromStep`/`catalog` from the master), then waits for the run. The child job itself calls `control.logPackageStart/End` via `packageRun`. |
| `package` node | `<Node>` | `notebooks/run_child_package.py` | same as a phase child, without a step around it. |
| `control` / `expression` | `<Node>` | `notebooks/control_node.py` | Applies the SSIS assignment (`wwi_orchestration.plan_expression.assign`) to the run's variable table and publishes it as a task value (e.g. `User::ExtractAttempt`). |
| `control` / `query` | `<Node>` | `notebooks/control_node.py` | Translates the T-SQL (`wwi_orchestration.tsql_translate`, legacy names -> `${catalog}.etl.*`), binds the `?` parameters from the plan, stores the single-row result in `result_variable`, publishes it. |
| `control` / `statement` | `<Node>` | `notebooks/control_node.py` | `EXEC etl.usp_LogError ...` -> `control.logError(...)`; other statements run as Spark SQL. |
| `reconcile` | `<Node>` | `notebooks/reconcile.py` | `control.assertRowCountReconciliation(spark, catalog, batchId, raiseOnFailure=True)`. |
| every root | `zz_close_batch_if_open` (`ALL_DONE`, depends on every sink) | `notebooks/close_batch_if_open.py` | If the graph ended without reaching `End_Batch` (a `Failure` edge terminated it) the batch is closed `Failed` with `control.endBatch(forceStatus="Failed")`, mirroring the `OnError` handler of the .dtsx. |

Task keys are the plan names with non-identifier characters replaced by `_`, clipped to 100 characters.
Every generated task carries a `description` marker (`plan-node: ... | kind=...`, `plan-child: <phase>/<package> project=...`,
`plan-edge: <from> -> <to> | value=... [expression=...]`) from which `tools/check_plan_parity.py` rebuilds
the node, child and edge sets and diffs them against the plan (run by `tests/test_generator.py`).

### Streams (parallelism)

The .dtsx generator splits a phase's children into `streams` sequence containers as `children[i::streams]`
and runs each lane serially (`build_orchestration_packages.py`). The job does exactly that: lane `i` is
a `depends_on` chain `__start -> child[i] -> child[i+streams] -> ...`, all lanes run in parallel, `__end`
depends on every lane tail. `MaxParallelStreams` is kept as a job parameter for the notebooks
(`run_child_package.py` passes it through) but the fan-out itself is fixed at plan time, as in the .dtsx.
Child runs are `run-now` calls, so the receiving project job's `max_concurrent_runs` must allow the widest
lane count in the estate (4, `Extract Oracle` / `Stage Load` / `Facts`) - see "Decisions needed".

### Edges

| Plan edge | Job wiring |
|---|---|
| `Success` without expression | `depends_on` of the downstream node's head task on the upstream node's terminal task (`__end` for phases). |
| `Success` with `expression` | `condition_task` gate `gate_<n>_<from>__<to>`: depends on the upstream terminal, condition `{{tasks.<terminal>.values.edge_<n>}} == "true"`; the upstream notebook evaluates the SSIS expression (`plan_expression.test`) over the current variable table and publishes `edge_<n>`. Downstream head depends on the gate with `outcome: "true"`. |
| `Failure` | gate with `run_if: ALL_FAILED` (an expression, if any, is evaluated the same way; `Failure` edges with no expression use a constant-true condition). |
| `Completion` | gate with `run_if: ALL_DONE`. |
| several incoming edges | downstream head uses `run_if: AT_LEAST_ONE_SUCCESS` - SSIS `LogicalOr`, which is how `Invoke-EstateOrchestration.ps1` fires a node once any predecessor edge is satisfied. |

`RestartFromStep` gates (`@[$Package::RestartFromStep] == "" || @[$Package::RestartFromStep] == "<Phase>"`)
are evaluated with the job parameter, so phases before the named step are skipped exactly where the plan
puts the expression.

### ExtractAttempt retry loop

Legacy: `Initialise Attempt Counter` sets `User::ExtractAttempt = 1`; after `Extract Oracle` /
`Extract SQL Server` a `Failure` edge leads to `Increment Extract Attempt`, `Record Extract Attempt`
(`etl.usp_LogError` warning) and the `Extract Retry Driver` phase (`ORCH_ExtractRetryDriver`), then the
`Extract Oracle Retry` / `Extract SQL Server Retry` phases re-run the packages, bounded by
`@[User::ExtractAttempt] < @[$Package::MaxExtractAttempts]`.

Mapping: the plan already unrolls the loop into one retry pass, so the graph is reproduced as-is
(counter, warning and driver are `control_node` tasks; the retry phases are ordinary phases). Two
additions make the retry pass behave like the SSIS loop rather than a blind re-run:

1. Retry-phase children run with `skipIfSucceeded=true`: `run_child_package.py` skips a package whose
   `etl.package_execution` row for this `BatchId` is already `Succeeded`, so only the failed objects are
   re-extracted.
2. Retry-phase children get task-level `max_retries: ${var.extract_retry_task_retries}` (default 1) and
   `min_retry_interval_millis: ${var.extract_retry_interval_millis}`; first pass + retry pass + one task
   retry = 3 attempts = the legacy `MaxExtractAttempts` default. Raising `MaxExtractAttempts` beyond 3
   therefore requires raising the bundle variable, which the doc-comment on the variable states.

### RestartFromStep

`Start_Batch` uses `allowAdoptRunning=True` when `RestartFromStep` is set (or `BatchId != 0`), adopting
the prior `Running` batch like `usp_StartBatch @AllowAdoptRunning = 1`. The `Restart Recovery` phase
(`ORCH_RestartRecovery`) runs `step_start.py` with `restartRecovery=true`, which marks the batch steps that
precede the named step as `Skipped` (`control.endBatchStep(..., status="Skipped")` after
`startBatchStep`), and the `RestartFromStep` gates above skip those phases' tasks.

## Job parameters (all strings)

`BatchId` (`"0"`), `BusinessDate` (`""` = `usp_StartBatch` default of today), `EnvironmentCode` (`"DEV"`),
`ReloadFullHistory` (`"False"`), `MaxParallelStreams` (`"4"`), `MaxExtractAttempts` (`"3"`),
`RestartFromStep` (`""`), `catalog` (`${var.catalog}`), plus the master-specific parameters from the plan
with their plan defaults (`SkipWhenNightlyRunning`, `AccountingPeriod`, `AllowCloseWithVariance`,
`FailOnCodeMapGap`, `SnapshotMonth`, `RebuildAllAggregates`, `MaintenanceWindowMinutes`, `SkipIndexRebuild`,
`SuppressConsentWithdrawn`, `DedupeThresholdScore`, `PickingWindowOpen`, `OnHandVarianceTolerance`,
`RequirePartnerFiles`, `QuarantineAfterAttempts`). Typed values are recovered with
`plan_expression.coerce(text, planDefault)`.

## Control framework usage

All control-table access is through `dbx_etl_common` (installed on the serverless environment from
`../../common/dbx_etl_common/dist/*.whl`); `notebooks/_bootstrap.py` is `%run` by every notebook and adds
`src/wwi_orchestration` (expression evaluator, T-SQL translator) to `sys.path`. No notebook writes to
`etl.*` directly.

## Not migrated / needs decision

| Item | Why |
|---|---|
| Project job `run_job_task` | The masters trigger `wwi_<NN_project>` with `only=[<Package>]` from a notebook (Jobs API `run-now`) instead of `run_job_task`, because `run_job_task` cannot restrict a run to one task and the project jobs are delivered by other PRs (no bundle-level `${resources.jobs...}` reference is possible across bundles). The job is resolved **by name** at run time; it must exist in the workspace before a master runs. |
| Project job `max_concurrent_runs` | Lanes fire several packages of the same project at once (up to 4). Each project job must allow `max_concurrent_runs >= 4` (or the masters queue on it). Decision for the project sessions / parent. |
| `MaxParallelStreams` | Legacy parameter existed but the .dtsx fan-out is fixed by `streams` in the plan; kept as a pass-through parameter only. |
| `MaxExtractAttempts > 3` | Task-level retries are a bundle variable, not a run-time parameter (see retry section). |
| `Master_Finance_Close` schedule time | Legacy shows "monthly day 1" without a time; 04:00 assumed (paused anyway). |
| `SkipIfSucceeded` for non-retry phases | Only retry phases skip already-succeeded packages; a manual re-run of a master with `RestartFromStep` re-runs every package of the named step and later (legacy behaviour). |
| Wheel path in `environments` | The masters install `../../common/dbx_etl_common/dist/*.whl` relative to the bundle root; if the platform team prefers a workspace/Volumes path for the shared wheel, switch `WHEEL_GLOB` in the generator (one line). |
| Legacy `OnError` e-mail / Agent notifications | Not in the plan; use job `email_notifications`/`webhook_notifications` when the addresses are decided. |
